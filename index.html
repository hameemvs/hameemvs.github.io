Selected work

Document Extraction Pipeline

A production service for a US healthcare DME provider that extracts structured clinical data from faxed/emailed documents with GPT-4o Vision — plus the data-integrity investigation that came with it.

  • Python
  • FastAPI
  • GPT-4o Vision
  • Quickbase API

Context

This system processes clinical documentation for a US healthcare durable medical equipment (DME) provider. Referring physicians and clinics send orders and clinical notes by fax and email; the pipeline extracts structured order and clinical data and writes it into the company's Quickbase system, which drives insurance documentation. Correctness matters directly — a wrong clinical statement doesn't stay internal, it goes out on a physician's letterhead in support of an insurance claim.

The Defect

Two email identifiers differed only in letter case, but the database matched them case-insensitively. Every time the differently-cased variant appeared, its record silently merged into the other instead of creating a new one. Over time this had quietly overwritten 148 of 902 email records and mis-parented 607 child rows under the wrong parent.

How It Was Found

I confirmed the pattern by checking whether each affected row had an absent "case-twin" — a record that should have existed under the differently-cased ID but didn't. To be sure the count was real, I ran the check independently and compared it against the client's own count, with neither side seeing the other's numbers first. They matched exactly. Separately, I recovered 895 identifiers from the client's Outlook mailbox with zero misses, giving a second, independent line of evidence for how many records should have existed.

The Fix & Migration

The permanent fix replaces the identifier with a case-normalized hash key, so two IDs that only differ by case can never collide again. I considered mapping to a canonical Quickbase Record ID instead, but record IDs get reassigned when rows are deleted and recreated during cleanup — a hash of the normalized email survives that. One detail mattered: the read path parsed identifiers the same case-sensitive way the write path did, so a fix that only touched writes would have left lookups broken; both had to change together. The database-side repair — restoring the merged and mis-parented records — was carried out by the client's data team; I diagnosed the collision, worked out the mechanism, and built the fix on the extraction/pipeline side, then migrated the live system with zero data loss.

What I'd Do Differently

The error-logging table meant to catch failures like this had never successfully written a single row — the code treated a partial-success HTTP status from the logging API as a full success, so every failure silently vanished instead of being recorded. Weeks of failures were invisible for exactly the reason you'd want them to be visible: nothing was watching the watcher. The lesson: error paths need testing as much as happy paths — a logging pipeline that's never seen a real failure in staging hasn't actually been tested.
